# app-gtf4.1 — Sambungkan pengirim/penerima jahit ke master

**Beads:** app-gtf4.1 · **GH:** (diisi setelah dibuat) · **Parent:** app-gtf4

## Konteks

6 kolom `text()` menyimpan nama orang/pihak yang sebenarnya sudah punya tabel
master. Diketik ulang tiap transaksi → salah ketik satu huruf bikin baris itu
hilang dari laporan tanpa error. Di Tahap 5 (HPP/keuangan) ini jadi **angka yang
salah**, bukan sekadar tampilan jelek.

## Keputusan yang sudah final (jangan ditawar ulang)

Semua sudah dikonfirmasi — sumbernya beda-beda, dicatat di sini supaya executor
tidak menebak:

1. **Pengirim/penerima = staf internal (`users`), BUKAN penjahit.**
   Bukti: blanko surat jalan klien memisahkan `PIC BARANG :` (staf) dari
   `PENJAHIT :` (tujuan). App lama klien juga punya master `PIC-` terpisah dari
   `VDR-`. Detail: `docs/insight-bisnis/istilah-vendor-penjahit-konveksi.md`.

2. **Tempat jahit cukup SATU daftar** — klien (Ucup, 21 Sep): *"kalo sekarang
   perorangan bukan perusahaan"*. Tidak ada CV/PT aktif.
   **TAPI** bentuk kolomnya tetap **2 kolom** (`vendorId` + `penjahitId`) mengikuti
   pola yang sudah ada di `penugasanJahit` (schema.ts:1094) dan `tarifJasaJahit`
   (schema.ts:1126) — lengkap dengan DB CHECK "tepat satu terisi". Alasannya:
   konsistensi dengan 2 tabel tetangga, dan nol migrasi lagi kalau klien nanti
   pakai CV (kata "sekarang" di jawaban klien = sinyal bisa berubah).

3. **TIDAK semua 6 kolom jadi FK.** Dua di antaranya orang di pihak vendor —
   kita tidak punya (dan tidak perlu) master karyawan vendor. Lihat tabel di bawah.

"siapa yang menerima **di vendor**" (placeholder form-nya memang
`"Nama di vendor"`), #5 itu "siapa yang menerima **di gudang kita**"
(placeholder `"Petugas gudang"`). Jangan tertukar.

## Task 1 — DB Migration ⚡ CLAUDE VIA MCP (bukan Antigravity)

```sql
-- === bundling: tujuanPenjahit → 2 kolom FK ===
ALTER TABLE bundling ADD COLUMN vendor_id uuid REFERENCES vendor(id);
ALTER TABLE bundling ADD COLUMN penjahit_id uuid REFERENCES penjahit(id);

-- Data dev: "CV Jahit Cibaduyut" → vendor VDR-0001,
--           "Penjahit Cibaduyut 1" → TIDAK ADA di master (baris hantu)
UPDATE bundling SET vendor_id = (SELECT id FROM vendor WHERE kode = 'VDR-0001')
WHERE tujuan_penjahit = 'CV Jahit Cibaduyut';

-- Baris hantu: biarkan kedua kolom NULL. CHECK di bawah pakai pola
-- "tidak boleh dua-duanya terisi" (bukan "tepat satu"), supaya baris
-- yang belum ditentukan tujuannya tetap sah.
ALTER TABLE bundling ADD CONSTRAINT bundling_tujuan_tunggal
  CHECK (NOT (vendor_id IS NOT NULL AND penjahit_id IS NOT NULL));

CREATE INDEX bundling_vendor_idx ON bundling (vendor_id);
CREATE INDEX bundling_penjahit_idx ON bundling (penjahit_id);
ALTER TABLE bundling DROP COLUMN tujuan_penjahit;

-- === pengirimanJahit.pengirim → FK users (nullable, boleh kosong) ===
ALTER TABLE pengiriman_jahit ADD COLUMN pengirim_id uuid REFERENCES users(id);
-- Data dev berisi nama penjahit ("Ujang Supriadi") — itu SALAH ISI sejak awal
-- (harusnya staf). Biarkan NULL, jangan dipetakan ke penjahit.
ALTER TABLE pengiriman_jahit DROP COLUMN pengirim;

-- === penerimaanHasilJahit.penerima → FK users ===
-- Kolom lama notNull. Tambah kolom baru nullable dulu, isi apa yang bisa,
-- lalu TIDAK dikunci notNull (lihat catatan di bawah).
ALTER TABLE penerimaan_hasil_jahit ADD COLUMN penerima_id uuid REFERENCES users(id);
-- Data dev berisi "Siti Aminah" (nama penjahit) — salah isi, biarkan NULL.
ALTER TABLE penerimaan_hasil_jahit DROP COLUMN penerima;
```

**Kenapa `penerima_id` TIDAK dikunci notNull** padahal kolom lamanya notNull:
master `users` saat ini baru berisi 1 baris (owner). Kalau dikunci sekarang,
form tidak bisa disimpan sama sekali sampai Abu selesai mendaftarkan staf.
Kunci notNull-nya dijadikan kartu lanjutan setelah akun staf terisi.

⚡ Dieksekusi Claude langsung saat sesi planning. Antigravity mulai dari Task 2.

**Catatan prod:** migration ini hanya untuk DB dev. Untuk prod, data teksnya
harus dipetakan manual dulu — nama yang ada di sana belum tentu sama.

Setelah migration, Claude juga update `src/db/schema.ts`:

```ts
// bundling (sekitar :970) — ganti tujuanPenjahit jadi:
    // DB CHECK bundling_tujuan_tunggal: tidak boleh vendor & penjahit dua-duanya terisi
    vendorId: uuid("vendor_id").references(() => vendor.id),
    penjahitId: uuid("penjahit_id").references(() => penjahit.id),

// pengirimanJahit (sekitar :1175) — ganti pengirim jadi:
    pengirimId: uuid("pengirim_id").references(() => users.id), // staf yang mengantar
    penerima: text("penerima"), // orang di pihak VENDOR — sengaja teks, kita tak punya masternya

// penerimaanHasilJahit (sekitar :1314) — ganti penerima jadi:
    penerimaId: uuid("penerima_id").references(() => users.id), // staf gudang kita
```

Plus tambahkan index pada argumen ketiga `pgTable` untuk bundling
(`bundling_vendor_idx`, `bundling_penjahit_idx`) — cek apakah tabel itu sudah
punya argumen ketiga; kalau sudah, tambahkan ke array yang ada.

Dan beri komentar alasan pada 3 kolom yang tetap teks (#3, #4, #6), formatnya
satu kalimat seperti contoh di atas — supaya tidak diaudit ulang.

## Kondisi yang HARUS diterima executor

Master `users` di dev saat ini **cuma 1 baris** (owner). Jadi setelah selesai,
dropdown akan menampilkan 1 pilihan saja. **Itu normal, bukan bug** — Abu yang
akan mendaftarkan staf lewat menu Pengguna secara manual.

Kriteria selesai untuk dropdown = **muncul dan menarik data dari tabel users**,
bukan "berisi banyak nama".
