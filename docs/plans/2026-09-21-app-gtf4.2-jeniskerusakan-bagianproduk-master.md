## Kenapa ini dikerjakan

`jenis_cacat` **sudah dipakai benar** sebagai FK di 4 tempat (`schema.ts:1643`,
`:1754`, `:1807`, dan satu lagi), tapi `returJahitDetail` masih teks bebas. Satu
modul mencatat hal yang sama dengan dua cara.

Akibatnya pertanyaan klien "cacat apa yang paling sering?" tidak bisa dijawab —
separuh datanya teks bebas yang tak bisa dikelompokkan.

`bagianProduk` melengkapi pasangannya: `jenisCacat` menjawab **cacatnya apa**,
`bagianProduk` menjawab **cacatnya di mana**. Dua-duanya perlu konsisten supaya
rekap QC bisa menunjuk titik masalah (mis. "60% cacat ada di kerah").

## Task 1 — DB migration ✅ SUDAH DIEKSEKUSI (Claude via MCP, 21 Sep sore, dev + prod)

Hasil verifikasi setelah dijalankan: `bagian_produk` berisi 10 baris di dev maupun
prod, ketiga kolom teks lama hilang, kolom FK baru ada, dan 2 baris `jenis_cacat`
milik klien di prod tetap utuh. Data teks yang ada (2 baris uji di dev) sengaja
dibiarkan NULL karena master dev kosong — tidak dipetakan ke tebakan.

Antigravity **mulai dari Task 2** dan tidak perlu menjalankan migration apa pun.
Isi di bawah adalah catatan apa yang sudah dijalankan.

### 1a. Tabel master baru `bagian_produk`

Ikut pola `jenis_cacat` (`schema.ts:1478`) — **partial unique index wajib**,
bukan `.unique()` flat (aturan proyek: kolom ber-`deleted_at` yang punya unique
harus partial, kalau tidak hapus-lalu-buat-ulang dengan kode sama akan crash 500).

```sql
CREATE TABLE bagian_produk (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  kode text NOT NULL,
  nama text NOT NULL,
  urutan integer NOT NULL DEFAULT 0,      -- urutan tampil, bukan identitas
  is_active boolean NOT NULL DEFAULT true,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  deleted_at timestamptz
);
CREATE UNIQUE INDEX bagian_produk_kode_active_unique
  ON bagian_produk (kode) WHERE deleted_at IS NULL;
```

`urutan` dipakai supaya daftar tampil mengikuti urutan fisik jaket (atas ke
bawah), bukan abjad. **Jangan** dipakai untuk menyimpulkan apa pun selain posisi
tampil (aturan proyek: derive dari kolom eksplisit, bukan kolom proxy).

### 1b. Isi awal `bagian_produk` (dev DAN prod)

Titik mulai, bukan daftar final. Klien boleh rename/hapus/tambah lewat halaman
master. Kode dibuat pendek dan stabil supaya rename nama tidak memutus relasi.

| kode | nama | urutan |
|---|---|---|
| BP-01 | Kerah | 10 |
| BP-02 | Bahu | 20 |
| BP-03 | Lengan | 30 |
| BP-04 | Badan | 40 |
| BP-05 | Saku | 50 |
| BP-06 | Resleting | 60 |
| BP-07 | Kancing | 70 |
| BP-08 | Jahitan Bawah | 80 |
| BP-09 | Label / Tag | 90 |
| BP-10 | Lainnya | 100 |

"Lainnya" sengaja ada: tanpa itu petugas QC yang menemukan cacat di bagian tak
terdaftar akan memilih yang salah, dan datanya jadi bohong.

### 1c. Kolom FK baru

```sql
-- returJahitDetail: teks -> FK jenis_cacat
ALTER TABLE retur_jahit_detail ADD COLUMN jenis_cacat_id uuid REFERENCES jenis_cacat(id);

-- standarQcDetail & temuanCacat: teks -> FK bagian_produk
ALTER TABLE standar_qc_detail ADD COLUMN bagian_produk_id uuid REFERENCES bagian_produk(id);
ALTER TABLE temuan_cacat      ADD COLUMN bagian_produk_id uuid REFERENCES bagian_produk(id);
```

Semua **nullable** — data lama tidak punya nilainya, dan memaksa NOT NULL akan
menolak baris yang sah.

### 1d. Migrasi data lalu buang kolom lama

**Dev:** 2 baris `returJahitDetail`. Nilainya (`"Jahitan bahu lepas"`,
`"Jahitan kerah bergelombang"`) tidak cocok persis dengan master mana pun —
master dev kosong. Biarkan `jenis_cacat_id` NULL, jangan dipetakan ke tebakan.
Itu data uji, bukan data nyata.

**Prod:** ketiga kolom teks kosong, jadi tidak ada yang perlu dipetakan.

Sudah diverifikasi baris per baris sebelum `DROP COLUMN` dijalankan: dev hanya
punya 2 baris teks uji, prod ketiga kolomnya seluruhnya NULL.

```sql
ALTER TABLE retur_jahit_detail DROP COLUMN jenis_kerusakan;
ALTER TABLE standar_qc_detail  DROP COLUMN bagian_produk;
ALTER TABLE temuan_cacat       DROP COLUMN bagian_produk;
```

### 1e. Update `src/db/schema.ts`

Tambah tabel `bagianProduk`, ganti tiga kolom teks jadi FK. Setelah ini muncul
error typecheck di pemakaian kolom lama — **itu disengaja**, jadi peta kerja
Antigravity.

## Task 2 — Halaman master Bagian Produk

Ikut pola master yang sudah ada. Referensi paling dekat: halaman Jenis Cacat
(`src/app/(with-layout)/master/jenis-cacat/`).

```
src/app/(with-layout)/master/bagian-produk/
  page.tsx                          ← Server Component, fetch + PageHeader
  _components/
    BagianProdukPageClient.tsx
    BagianProdukTable.tsx
    BagianProdukFormModal.tsx
```

- Service: `src/services/bagian-produk.ts` — CRUD + soft delete, `requireRole`
  mengikuti service master sejenis
- Zod: `src/lib/schemas/bagian-produk.ts`
- Hook: `src/hooks/useBagianProduk.ts`
- Kode auto-generate `BP-NNNN` lewat `generateDocNumber` — **jangan bikin
  generator baru**
- Guard duplikat: cek `isNull(deletedAt)` sebelum insert, untuk pesan error yang
  bagus. DB-nya sendiri sudah dijaga partial unique.

⚠️ **Regex di postgres.js:** kalau generator kode memakai `regexp_replace`,
tulis `'\\D'` bukan `'\D'` — postgres.js membuang backslash tunggal di tagged
template. Pernah kena di 3 fungsi generate kode (lokasi/vendor/penjahit).

### Nav

Tambah entri di `src/components/layouts/sidebar/data/index.ts`, grup **Master
Data**, dekat "Jenis Cacat" (heading "Data QC").

⚠️ Sidebar sekarang punya filter role (`app-qr6o`, 21 Sep). Entri baru **tanpa**
`roles` = terlihat semua role — itu benar untuk master ini, karena master lain di
grup yang sama juga belum punya `requireRole`. Jangan menambah `roles` yang lebih
ketat dari yang dienforce service.
